# ESP32-S3 WiFi Print Server (LPT / Centronics) — универсальный

Порт проекта [gianluca-nitti/printserver-esp8266](https://github.com/gianluca-nitti/printserver-esp8266) на **ESP32-S3-DevKitC-1 N16R8** с расширенным функционалом: прямое управление LPT без сдвигового регистра, все статусные линии принтера, OLED-индикация, печать с Android и ПК по сети. Прошивка **не привязана к модели принтера** — работает с любым Centronics-принтером, понимающим PCL.

Прошивка собирается **PlatformIO** (уже собрана, см. `firmware/`) и **Arduino IDE 2** (скетч `printserver.ino`; см. раздел «Сборка» — важное про пустой .ino).

---

## Подключение (DB25 принтера → ESP32-S3)

**Важно:** ESP32-S3 — устройство 3.3 В. Выходы ESP32 на линии данных/STROBE/INIT/SELECTIN/AUTOFD читаются принтером (5В TTL) как валидные уровни напрямую. Обратные линии принтера (5 В) **обязательно** делить резисторами: 10 кОм (со стороны принтера) + 20 кОм (на GND) дают ~3.3 В на входе GPIO.

| DB25 (принтер) | Сигнал | Направление | GPIO ESP32-S3 | Примечание |
|---|---|---|---|---|
| 2–9 | D0–D7 | ESP32 → принтер | 4, 5, 6, 7, 10, 11, 12, 13 | напрямую |
| 1 | /STROBE | ESP32 → принтер | 14 | напрямую |
| 10 | /ACK | принтер → ESP32 | 15 | делитель 10к/20к |
| 11 | BUSY | принтер → ESP32 | 21 | делитель 10к/20к |
| 12 | PAPER END | принтер → ESP32 | 16 | делитель 10к/20к |
| 13 | SELECT | принтер → ESP32 | 17 | делитель 10к/20к |
| 15 | /ERROR | принтер → ESP32 | 18 | делитель 10к/20к |
| 16 | /INIT | ESP32 → принтер | 38 | напрямую |
| 17 | /SELECT IN | ESP32 → принтер | 39 | напрямую, держать LOW |
| 14 | /AUTO FEED | ESP32 → принтер | 40 | напрямую, держать HIGH |
| 18–25 | GND | общий | GND | обязательно все, параллельно |
| — | OLED SDA/SCL | | 8 / 9 | I2C 0x3C |
| — | кнопка BOOT | | 0 | уже на плате DevKitC-1; удержание 3 с = AP |
| — | RGB LED | | 48 | уже на плате (WS2812); опционально простой LED на GPIO2 |

Пины выбраны так, чтобы не задеть: strapping (0, 3, 45, 46), SPI-флеш (26–32), PSRAM octal (33–37), USB (19/20).

## Сборка и прошивка

### PlatformIO (рекомендуется)

```bash
pip install platformio
pio run                    # сборка
pio run -t upload          # прошивка (USB-C DevKitC-1)
pio device monitor         # лог 115200
```

### Arduino IDE 2

Установить поддержку «esp32 by Espressif Systems»; плата **ESP32S3 Dev Module**, Flash Size 16MB, PSRAM: OPI PSRAM, USB CDC On Boot: Enabled. Открыть `printserver.ino` и собрать.

**Про структуру:** раскладка плоская, как в оригинальном проекте — все `.cpp/.h` лежат рядом с `printserver.ino`, а `setup()`/`loop()` находятся в самом `.ino`. Arduino IDE и PlatformIO (конфиг `platformio.ini` с `src_dir = .`) собирают всё одинаково; отдельного `main.cpp` нет.

Готовые артефакты в `firmware/`: `firmware_<версия>.bin` (имя файла несёт версию сборки), `bootloader.bin`, `partitions.bin` (загрузка: `esptool.py --chip esp32s3 write_flash 0x0 bootloader.bin 0x8000 partitions.bin 0x10000 firmware.bin`).

### Обновление прошивки по воздуху (OTA)

Первая прошивка — только по USB (см. выше). Дальше обновляться можно без кабеля:

1. Откройте веб-панель → ссылка **«Обновление прошивки»** (или сразу http://IP/update). Страница показывает текущую версию.
2. Выберите `.bin`, собранный под ESP32-S3: из своей сборки (`pio run` → `.pio/build/esp32s3/firmware.bin`; Arduino IDE → «Скетч → Экспорт бинарного файла») или готовый `firmware/firmware_<версия>.bin` из репозитория. Образ ESP8266/чужой файл загрузится с ошибкой проверки (нет магического байта 0xE9) — текущая прошивка при этом не пострадает.
3. Нажмите «Загрузить и прошить» — прогресс-бар до 100 %, затем устройство само перезагружается в новый образ (~15 с), страница предложит вернуться в панель.

**Как узнать, какая версия загружена:** версия прошивки — первой строкой в таблице статуса на главной странице http://IP/, в подвале страницы настройки WiFi и на странице обновления. Каждая доработка прошивки поднимает `FIRMWARE_VERSION` в `config.h` (значимые фичи — младший номер, мелкие правки — патч), так что по панели всегда видно, какой образ стоит на устройстве.

Как это устроено: во flash два 4-МБ слота приложений (`app0`/`app1`, см. `partitions-16mb.csv`). Работающий образ не трогается — новый пишется в свободный слот, проверяется (контрольная сумма + магический байт 0xE9 образа ESP32) и активируется только после полной записи. Обрыв передачи или питания в процессе оставляет текущую прошивку рабочей. На время печати обновление блокируется (страница предупреждает, POST отвечает 503) — запись во flash занимает процессор на всю передачу, а перезагрузка убила бы задание на середине страницы.

Опциональный пароль: в `config.h` задайте `OTA_PASS "свой-пароль"` — страница запросит его при обновлении (передаётся заголовком `X-OTA-Key`). Пустой `OTA_PASS` (по умолчанию) = обновление открыто всем в локальной сети — та же модель доверия, что у страницы настройки WiFi.

## Использование

1. Первый запуск: OLED «подключение к wifi...» → «AP 192.168.4.1». Подключитесь к сети `ESPPrintServer-XXXX`, откройте http://192.168.4.1/wifi — страница покажет **список найденных сетей** (сигнал, открытая/закрытая); клик по сети подставит её SSID, останется ввести пароль. Сети отсортированы по алфавиту. Можно и ввести SSID вручную (кнопки «Ручной ввод» внизу). Пробелы и спецсимволы в пароле поддерживаются.
2. После подключения OLED: «IP 192.168.x.x», вторая строка — `ESPPrint-XXXX.local` (длинное имя прокручивается). Если принтер не подключён по LPT, на второй строке «принтер не подключен» (после подключения принтера — «готов»).
3. **Windows:** любой PCL-драйвер (например «HP Universal Printing PCL» или Generic / Text Only) → порт Standard TCP/IP, **RAW 9100**. Или IPP: `http://IP:631/lp`.
4. **Linux/macOS CUPS:** `lpadmin -p LPT -E -v socket://IP:9100 -m drv:///generic/generic.ppd` (для PCL-принтера — его PPD), или `ipp://IP/lp`.
5. **Android — печать без приложений (системная служба):**
   - Телефон и принт-сервер в одной WiFi-сети.
   - Система: Настройки → Подключённые устройства → Подключения → Печать (или «Печать по умолчанию», зависит от версии Android) → **Системная служба печати**.
   - Принтер `ESP LPT PrintServer` появится в списке **автоматически** через несколько секунд (mDNS `_ipp._tcp`). Нажмите на него — скачаются «возможности» (Get-Printer-Attributes).
   - Если принтер не появился автоматически: в той же службе есть «Поиск принтеров в Wi-Fi сети» / «Все принтеры» → он должен быть там. **Ввод IP вручную** (`192.168.1.45`) во многих прошивках Android работает только для IPP-принтеров с полным профилем; если вручную пишется «принтер не поддерживается» — это нормально для урезанного клиента: используйте автопоиск по mDNS (основной путь) или обновите прошивку принт-сервера до этой версии, где `document-format-supported` содержит `image/pwg-raster` (раньше Android его не находил и отклонял принтер).
   - Печать: «Поделиться» → Печать, или из приложения. Android сам отрендерит документ в PWG-raster (300 dpi, ч/б), прошивка сконвертирует в PCL и выведет на LPT.
   - Веб-панель http://IP/ покажет состояние и очередь.
6. Индикация: «Загрузка данных» → «печать...»; «нет бумаги»/«ошибка» — задание ждёт в очереди, продолжится после устранения проблемы. Если принтер подключён, но выключен/офлайн — «офлайн», задание тоже ждёт и продолжится при включении принтера. Если к порту ничего не подключено — задание сбрасывается через ~3 с с «нет ответа LPT» (ящик и сеть продолжают работать).

## Индикация светодиодом и кнопка

Состояние дублируется встроенным RGB-светодиодом DevKitC-1 (GPIO48, `PIN_LED_RGB` в `config.h`) — на случай, если OLED не работает или не установлен. Если платы без WS2812 — можно повесить простой светодиод на GPIO2 (`PIN_LED_WIFI`, анод через резистор ~470 Ом), он мигает те же паттерны. «255» в `config.h` = элемент не используется.

| Цвет | Режим | Что означает |
|---|---|---|
| синий | мигание 2 Гц | подключение к WiFi («Подкл. к ХХХ» на OLED) |
| зелёный | горит | подключено к WiFi |
| жёлтый | мигание 1 Гц | режим точки доступа (настройка; после удержания кнопки — «настройка», иначе «сеть не найдена») |
| голубой | мигание 5 Гц | приём задания |
| малиновый | мигание 5 Гц | печать |
| красный | мигание 4 Гц | принтер требует внимания: нет бумаги / ошибка (печать остановлена, задание в очереди) |

**Кнопка BOOT** (GPIO0, `PIN_BTN`): удержание ~3 с (`BTN_HOLD_MS`) в любой момент — включая время, когда прошивка «зависла» в подключении к плохой сети, — принудительно разрывает WiFi и открывает точку доступа `ESPPrintServer-XXXX` для переконфигурации. На OLED «настройка» вместо «сеть не найдена». Фоновые попытки вернуться на старую сеть выключены, пока не будут сохранены новые креденшлы через веб-панель (или не появится сохранённая сеть — при обычном, некнопочном AP-режиме ретраи каждые 2 минуты остаются).

## Проверка перед первым включением (безопасность принтера)

ESP32-S3 — только 3.3 В, ни один его GPIO не 5В-толерантен. Оригинальный проект обсуждал это в issues [#15](https://github.com/gianluca-nitti/printserver-esp8266/issues/15) (3.3 В достаточно для входов принтера: IEEE 1284 требует V_IH ≥ 2.4 В) и [#18](https://github.com/gianluca-nitti/printserver-esp8266/issues/18) (общий GND обязателен, 5В-выходы принтера — через делитель). Чек-лист перед подачей питания:

1. **Направления сигналов** — перепроверьте по таблице выше: D0–D7, STROBE, INIT, SELECT IN, AUTO FEED идут ОТ ESP К принтеру (напрямую, делителей не нужно); BUSY, ACK, PE, SELECT, ERROR идут ОТ принтера К ESP — **только через делитель 10к/20к** (5 В → 3.3 В). Прошивка сама настраивает направления (`ParallelPort::begin()`), но она не может исправить физическое подключение.
2. **Делители на месте**: прозвоните каждый вход ESP со стороны DB25 — при отключённом принтере на ноге должно быть ~0 В (или уровень делителя при подключённом), никогда 5 В.
3. **GND**: все контакты 18–25 DB25 на GND платы ESP. Без общей земли «странные» ошибки передачи (issue #18 оригинала).
4. **Прошивка никогда не переключает статусные линии на выход** — единственный источник опасности для принтера это если бы ESP стал выдавать 3.3 В на 5В-выход принтера (конфликт двух драйверов). В коде `PIN_LPT_*` входные пины инициализируются только `INPUT`/`INPUT_PULLUP`/`INPUT_PULLDOWN`, выходы — только пины управления. Но если пины менялись в `config.h`, проверьте, что новые номера не конфликтуют (см. ниже).
5. **Занятые пины не переносить**: strapping 0/3/45/46 (0 — кнопка BOOT), флеш 26–32, octal-PSRAM 33–37, USB 19/20, I2C OLED 8/9. GPIO21 (BUSY) — обычный свободный пин. GPIO38–40 — допустимые выходы (INIT/SELECT IN/AUTO FEED); на платах с quad-PSRAM GPIO38 занят PSRAM — тогда INIT придётся перенести.
6. **Первый запуск — с мультиметром**: подайте питание без кабеля принтера, проверьте на контактах DB25-вилки STROBE ≈ 3.3 В (idle), данные ≈ 0, INIT ≈ 3.3 В; только потом подключайте принтер.

## Исправленные ошибки оригинала

1. **Хендшейк LPT** (`ParallelPort.cpp`): в оригинале данные выставлялись и STROBE дёргался без времени установки, и после STROBE не ждался цикл BUSY — на быстром ESP32-S3 это теряло байты (пропуски строк, битые символы). Теперь: setup ≥1 мкс, импульс STROBE 2 мкс, ожидание цикла BUSY с таймаутом.
2. **Очередь** (`PrintQueue.cpp`): `byte head/tail` переполнялись после 255 заданий. Теперь 32-битные монотонные ID + каталог `/q/` + чистка мусора при загрузке.
3. **WiFi-креды** (PR #1/#2): urlDecode и `WiFi.persistent(true)` — интегрированы.
4. **Блокирующие чтения**: вместо `waitAvailable()` с `delay(10)` — асинхронный pump.
5. **IPP**: атрибуты multi-value теперь корректны (имя только у первого значения, остальные с name-length 0), `printer-state` — настоящий enum, `printer-is-accepting-jobs` — boolean; добавлены `pwg-raster-document-*`, поддержка chunked и Expect: 100-Continue.
6. **PWG-декодер** (этой ревизии, найдено повторным ревью): (а) ширина входной строки проверялась против выходного 1-битного буфера — страницы шире ~300 px отвергались; (б) 1-битный растр (black_1, половина клиентов Android) декодировался как 8-битный серый; (в) заполнение по ctl=128 в K-пространстве делалось белым, хотя CUPS заполняет чёрным — почти чёрные страницы; (г) `pwg-raster-document-type-supported` заявлял только black_1, теперь black_1 + sgray_8 + srgb_8 (рекомендация автора PWG). Полярность битов 1=белый подтверждена по эталонному драйверу `rastertohp` (CUPS пишет строки в PCL байт-в-байт).
7. **IPP Print-Job при полном диске** теперь отвечает server-error-device-error (0x0503) вместо «успех» с молча потерянным заданием.
8. **Буферы декодера и repeat-руны** (второе повторное ревью, host-тесты воспроизводят): (а) `pclRow` был `2550/8 = 318` байт вместо `(2550+7)/8 = 319` — последний байт строки US Letter (8.5″ @300dpi) писал мимо конца массива и портил соседний `lineBuf` (белые артефакты в начале строк); (б) repeat-руны (ctl 0..127) для srgb_8 писали 1 байт на пиксель вместо 3 — строка не завершалась и терялась молча; (в) `lineBuf` 2550 Б отвергал заявленный в IPP полноширинный srgb_8 (A4 = 7440 Б, Letter = 7650 Б) — теперь 2550×3 Б; (г) страницы шире 2550 px (например 600 dpi) отвергаются честно по `hdrW`, а не переполняют `pclRow`.
9. **IPP chunked-transfer**: ожидание CRLF после чанка не имело рабочего таймаута (счётчик не инкрементировался) — зависший клиент вешал спулинг до watchdog-reset; теперь ожидание ограничено 1 с, после чего спул корректно завершается.
10. **Слоты спула**: raw 9100 и IPP делят `MAX_RAW_CLIENTS` слотов, а `PrintQueue` рассчитана на `MAX_CONCURRENT_JOBS = 4` — при 2 слотах половина ёмкости очереди была недостижима; выровнено (`MAX_RAW_CLIENTS = MAX_CONCURRENT_JOBS`).
11. **Таймаут LPT**: перед сбросом полураспечатанного задания пытаемся восстановить зависший интерфейс INIT-пульсом (`resetPrinter()`) с коротким повтором — часто спасает страницу; сброс только если не помогло.
12. **Многостраничная печать PWG** (третье ревью, воспроизводится host-тестом): repeat-кодированная строка — это `rowRepeat` СТРАНИЦЫ строк, а `inRow` рос на 1 за единицу кодирования — страница с повторами никогда не «завершалась», заголовок следующей страницы декодировался как мусорные строки (`bad header`, потеря страниц). Теперь `inRow += rowRepeat`.
13. **Потеря заданий после перезагрузки** (`PrintQueue`): `cleanupStale()` разбирал только `.ok`, игнорируя `.okw` (PWG-задания Android) — после ребута `nextId` сбрасывался в 1 и новое задание молча ЗАТИРАЛО старейшее `.okw` в очереди. Теперь id учитываются для обоих форматов; `pending` при загрузке тоже честный.
14. **State-машина движка** (`printserver.ino`): вход raw/IPP-клиента во время печати перезаписывал `engState=RECEIVING`, а возврат в IDLE рестартил PWG-декодер на читателе СЕРЕДИНЫ файла → `bad sync` → печатающееся задание сбрасывалось. Переходы RECEIVING↔IDLE теперь условные: спулинг идёт параллельно печати (очередь на это и рассчитана), декодер не перезапускается.
15. **Отказ LPT при конвертации PWG**: колбэк вывода игнорировал неудачу `writeByte` (декодер не прерывался) — при мёртвом принтере каждый байт ждал полный таймаут 120 с, задание не завершалось никогда. Теперь INIT-восстановление + честный abort («нет ответа LPT» на OLED).
16. **Переполнение флэша посреди задания**: запись в полный LittleFS молча теряла хвост — усечённый `.ok` печатал полстраницы, клиенту отвечалось «успех». Теперь неудача записи — липкий флаг: `endJob()` выбрасывает усечённое задание, IPP отвечает `server-error-device-error` (0x0503); raw 9100 отказывает в подключении при нехватке места.
17. **IPP-корректность**: (а) на неподдерживаемую операцию (Get-Jobs и т.п.) ответ был малформирован — статус «success» + два мусорных байта вместо атрибутов, без end-of-attributes; теперь честный `client-error-operation-not-supported` (0x040C); (б) `printer-state` дублировался (keyword «idle» + enum 3 с конфликтом типов); (в) `queued-job-count`/`copies-default`/`printer-up-time` шли строками вместо integer/enum — теперь бинарные типы по RFC 8011, значения живые (processing при печати, реальный размер очереди, приём заданий привязан к месту на флэше).
18. **Глубина цвета и формат бумаги**: 16-битный серый раньше проваливался в ветку «3 байта/пиксель» (мусор на бумаге) — теперь честный отказ «unsupported bit depth»; PCL-код страницы выбирается по PageSize заголовка (Letter 612 pt → 2A, A4 → 26A) — раньше Letter-растр объявлялся A4 и обрезался принтером.
19. **Граница заданий в очереди** (четвёртое ревью): `hasData()` молча переключает reader на следующее задание, а движок печати продолжал гнать его байты через настройку ПРЕДЫДУЩЕГО задания. При двух и более заданиях в очереди: `.okw` после `.ok` уходил в порт сырыми байтами (мусорные страницы), а что угодно после `.okw` попадало в живой декодер («bad sync»/«bad header») и сбрасывалось. Корректно печатало только одно задание в очереди. Теперь движок детектирует смену `currentJobId()` внутри 512-байтового цикла и на границе вызывает `engineSwitchJob()`: завершает растр (`pwg.end()` — конец графики + прогон ленты), при необходимости запускает свежий декодер. Контракт очереди (id+формат переключаются, пока данные ещё есть) закреплён хост-тестом на настоящем littlefs.
20. **Зависание на «текущем» клиенте**: дрен HTTP/IPP-заголовков не имел лимита строк — клиент, отдающий заголовки по ~0.9 с, держал цикл бесконечно (ящик перестаёт обслуживать сеть и LPT). Теперь максимум 40 строк заголовков на запрос.
21. **Самовосстановление очереди**: файл, который виден в каталоге, но не открывается (повреждение littlefs), раньше выбирался `hasData()` снова на каждой итерации loop() — горячий цикл неудачных open. Теперь такой файл удаляется, счётчик `pending` корректируется.
22. **Ping-pong-скролл OLED** (пятое ревью, host-тест `test_scroll` воспроизводит): формула сворачивала вторую половину периода при shift>16 — длинная строка (SSID, «Подкл. к …») уезжала на 16 px, затем ПРЫГАЛА на дальний конец (скачок до 59 px при строке 204 px) и медленно возвращалась; левого прохода не было вовсе. Счётчик кадров `uint8_t` к тому же переполнялся на 128 полу-шагах — широкие строки не завершали цикл. Теперь честная треугольная волна (моно-ход влево до −(w−128)−16, разворот, ход вправо, шаг ≤1 px/кадр, период 4·span кадров, счётчик `uint32_t`).
23. **Обрезанные IPP-передачи финализировались как успешные**: клиент, обещавший `Content-Length: N` и приславший меньше (обрыв сети), или chunked-поток без терминального чанка `0\r\n` — спулился, задание финализировалось, печаталась полстраницы, клиенту отвечалось «успех». Также пустая строка chunk-заголовка (таймаут `readStringUntil`) считалась терминальным чанком. Теперь обрыв трекается (`sawTerminal`/`remaining`), задание отменяется, клиенту честный `client-error-bad-request` (0x0400); при заполненной флэше остаётся `server-error-device-error` (0x0503). Заодно: разбор атрибутов IPP больше не крутится до 10-с потолка при умершем сокете — ранний выход по `!connected()`.
24. **120-с ступор при выключенном/отсутствующем принтере**: `writeByte()` ждал полный `LPT_BUSY_TIMEOUT_MS` (120 с — это запас на протяжку листа при BUSY), когда SELECT просто LOW (принтер выключен/офлайн/порт пуст) — весь ящик, включая веб-панель, замерзал на две минуты на каждое задание. Теперь секундный устойчивый deselect = быстрый отказ: INIT-восстановление, короткий повтор, честный сброс с «нет ответа LPT» (~3 с вместо 122). Принтер, который ЗАВИСЕН как подключённый (SELECT когда-то поднимался), но сейчас выключен — задание ставится на паузу («офлайн» на OLED) и продолжается с того же байта при включении принтера; порт, где SELECT никогда не поднимался, не копит задания молча.
25. **Raw 9100: призрачные клиенты** занимали слоты навсегда (полуоткрытый TCP после падения отправителя не закрывается сам) — четыре призрака и печать встаёт до ребута. Теперь слот, не получавший байт `RAW_IDLE_TIMEOUT_MS` (5 мин), закрывается, неполное задание отбрасывается.
26. **Политика перезагрузки: очередь обнуляется** (запрос пользователя): каждое включение начинает с пустой очереди — годовой давности спул не должен вываливаться на подключенный позже принтер «загадочными файлами». `PrintQueue::begin()` вычищает весь `/q` (`.ok`, `.okw`, `.tmp`), id продолжаются дальше максимума (свежие задания не наезжают на имена, на которые может указывать устаревший job-uri), в serial — `[q] reboot policy: purged N job(s)`. Заодно добавлены логи видимости: `[ipp] <строка запроса>` при каждом IPP-подключении, `[ipp] Print-Job stored/DENIED: N B (job M)` — вердикт по заданию, `[raw] connect accepted/refused` — вход на 9100; раньше «телефон стучался — не стучался» в мониторе не было видно вообще.
27. **Прозрачность IPP-соединений**: Android/HyperOS добавляет принтер по голому IP и сам простукивает 631/9100; если его ответ не устроил — задание молча не уходит, а в мониторе пусто. Теперь каждая строка запроса и каждый вердикт логируются — по монитору видно, дошёл ли клиент до ящика и на каком шаге отвалился.
28. **Chunked-тела IPP читались мимо декодирования** (полевой тест 2.4.0, хост-тест `test_ippbody`): 8-байтовый IPP-заголовок и разбор атрибутов читались напрямую из сокета, и при `Transfer-Encoding: chunked` строки размеров чанков («5\r\n», «0\r\n») попадали в парсер как байты IPP: мусорный operation-id → `client-error-operation-not-supported` → телефон бескончно ретраил задание (десятки `POST /ipp/print` без единого вердикта в мониторе). Весь путь чтения (заголовок, атрибуты, документ) теперь идёт через один `ipp::BodyStream` (`IppBody.h/.cpp`, host-тестируемый): Content-Length и chunked дают единый поток байтов, обрыв/усечение трекаются (`sawTerminal`/`remaining`), запросы без framing получают HTTP 400 вместо молчаливого drop-соединения. Побочные эффекты той же серии: каждое закрытие IPP-сессии логирует статус-код (`[ipp] op=0x0002 -> successful-ok`), пустые строки запроса логируются как пробы портов.
29. **Android-протокол и «призрачные» артефакты**: (а) **Create-Job → Send-Document** (двухшаговая схема, которую реально использует Android print backend) + Get-Jobs / Get-Job-Attributes / Cancel-Job — `operations-supported` честно перечисляет все поддерживаемые операции, Cancel-Job реально удаляет ожидающее задание из спула (`PrintQueue::removeJobById`, host-тест группа 10); (б) **ленивый raw-спул**: Android при добавлении принтера открывает 4 соединения к 9100 и закрывает их без байта — раньше каждое открывало `.tmp`-файл и вешало «Загрузка данных» на OLED (после ребута — «purged 4 queued job(s)»); теперь спул-файл/слот/экран занимаются только при первом байте; (в) **раздельные имена сервисов** (запрос пользователя): `_ipp._tcp` → «ESP32 WiFi_to_LPT (IPP)», `_pdl-datastream._tcp` → «ESP32 WiFi_to_LPT (socket)» — в списке Android больше нет двух неотличимых записей с одинаковым именем; (г) полный спул отвечает `server-error-not-accepting-jobs` (0x0506) вместо device-error.

## Известные ограничения / TODO

- LPD-сервер (515) не начат.
- Конвертер PWG→PCL: принимает `black_1` (1-бит, бит 1 = белый, MSB-first — по семантике CUPS `rastertohp`), `sgray_8` (порог gray<128 → чёрный) и `srgb_8` (BT.601 luma + тот же порог); CMYK, 16-битные и прочие глубины/цвета честно отвергаются с ошибкой в лог. Формат страницы PCL выбирается по PageSize заголовка (A4/Letter), буферы рассчитаны на 8.5″ = 2550 px @300dpi.
- AirPrint (iOS) требует `_ipp._tcp` + `_universal._sub._ipp._tcp` и URF-декодера (`image/urf`) — **не планируется**: в хозяйстве только Android и ПК, им хватает PWG-raster/raw-9100.
- Хост-тесты: `tests/run_tests.sh` — пять наборов без железа. (1) Декодер (`test_pwg`): 8-битный серый с повторами строк, полная ширина A4, black_1 с заполнением 128 (чёрный в K-пространстве), srgb_8, отказ на CMYK; регрессии второго ревью — Letter во всю ширину, srgb_8 с repeat-рунами, отказ 600 dpi, полноширинный srgb_8; третьего — многостраничный поток, прерывание при отказе вывода («output stalled»), отказ 16-битной глубины, PCL-код A4/Letter по PageSize. (2) Очередь (`test_queue`, 94 проверки): PrintQueue исполняется на НАСТОЯЩЕМ littlefs в RAM (`tests/host_littlefs/` — vendored littlefs 2.9 + Arduino-шим): round-trip, контракт границы заданий (id+isPwg переключаются при непрочитанных данных), политика ребута (очередь обнуляется, `purgedAtBoot` считает все форматы, id уходят дальше максимума), чистка `.tmp`, отмена/пустые задания, параллельные writer'ы, переполнение флэши (задание отбрасывается), Cancel-Job (`removeJobById`: удаление по id с сохранением порядка, отказ для задания на печати, `.okw`-флейвор). (3) Транспорт IPP (`test_ippbody`, 22 проверки, 2.4.0): Content-Length и chunked декодирование через один `BodyStream`, терминальный чанк, флаги усечения, обрыв в середине чанка, мусорная строка размера, побайтовая выдача, hex в верхнем регистре. (4) Траектория ping-pong-скролла OLED (`test_scroll`, 12 проверок): линкуется настоящий `StatusDisplay.cpp` со стабами — нет скачков (шаг ≤1 px), оба прохода монотонны, амплитуда [−(w−128)−16, 0], периодичность, полный цикл широких строк (пятое ревью). (5) Синтакс-проверка всех модулей прошивки компиляцией на хосте (`tests/host_syntax/`), включая `IppBody.cpp`.
- Спулинг и печать идут параллельно: задание печатается из очереди, пока следующее принимается; PWG-декодер не перезапускается при входе новых клиентов. При переполнении флэши посреди приёма задание отбрасывается целиком (полупустая страница не печатается), IPP-клиенту отвечается 0x0503; при обрыве передачи (меньше байтов, чем обещал Content-Length, или chunked без терминального чанка) — 0x0400.
